# 1 · The ESA-ADB dataset — what's actually in it

Every number and example below was pulled from the real files, not from the paper's description.

---

## The mental model

A satellite carries hundreds of sensors (temperature, voltage, pressure, gyro rates…). Each
reports a number periodically, forever. ESA took ~14 years of this from one real spacecraft
(**Mission 1**) and ~3.5 years from another (**Mission 2**), anonymised it, and had human
operators mark the periods where something went wrong.

**Your job:** given the sensor streams, find those periods automatically.

---

## The five file types

### 1. `channels/channel_N.zip` — the telemetry

Pickled pandas DataFrames. Real slice of `channel_41`:

```
                         channel_41
datetime
2009-01-23 19:24:24.942    0.804729
2009-01-23 19:24:54.942    0.801590
2009-01-23 19:25:24.942    0.804729
2009-01-23 19:25:54.942    0.803160
2009-01-23 19:26:24.942    0.952286   ← something starts
2009-01-23 19:26:27.030    0.969553   ← only 2.09 s later!
2009-01-23 19:26:47.442    0.818072
2009-01-23 19:26:54.942    0.803160
```

Three things to notice:

1. **15.4 million rows for one channel** (2000-01-01 → 2013-12-31). × 76 channels ≈ 1 billion numbers.
2. **Timestamps are irregular.** Mostly 30 s apart, but not always — note the 2.09 s gap.
   Different channels tick at *different* rates. **This is the single most important technical
   fact about the dataset** — you cannot form a matrix from 76 streams that tick at different,
   irregular times. Fixing it is the entire point of preprocessing.
3. **Values are pre-normalised to ~0–1.** ESA anonymised them, so `0.8126` means nothing physical.

Measured sampling behaviour (Mission 1):

| Channels | Dominant interval | Notes |
|---|---|---|
| 1–3 | 3 s (52 %) | bimodal 3 s / 90 s |
| 4–11 | 180 s (45 %) | **counters** — see preprocessing |
| 12–13, 17–20, 25–28, 34–37 | 0.38 s (58 %) | burst mode; ~81 samples per 30 s window |
| **41–46** | **30 s (90.3 %)** | **the lightweight benchmark subset** |
| 47–49, 53–60, 70–76 | 30 s (>99 %) | very clean |
| 61–63 | 900 s | slowest |

> The 0.38 s channels are in burst mode for only **0.77 % of the timeline** (39 days out of 14
> years) — those bursts dominate the *sample count* but are almost invisible in *elapsed time*.

### 2. `channels.csv` — what each channel is

```
     Channel    Subsystem    Physical Unit  Group Target
40  channel_41  subsystem_5  physical_unit_4     8    YES
41  channel_42  subsystem_5  physical_unit_4     8    YES
...
45  channel_46  subsystem_5  physical_unit_4     8    YES
```

This explains a lot. Channels 41–46 are all in the **same subsystem, same physical unit, same
group** — six instruments bolted to the same hardware. We measured them at **97–100 % correlated**.
They are effectively six thermometers on one panel.

- **Target = YES** → this channel has annotations and is evaluated. Only **58 of 76** M1 channels are targets.
- **Group** → physically related channels.

### 3. `labels.csv` — where the anomalies are (3,589 rows)

```
     ID     Channel                 StartTime                   EndTime
0  id_1  channel_12  2004-12-01T20:42:15.429Z  2004-12-08T22:55:45.429Z
1  id_1  channel_13  2004-12-01T20:42:15.429Z  2004-12-08T22:55:45.429Z
...
29 id_1  channel_41  2004-12-02T03:07:17.646Z  2004-12-08T23:35:55.146Z
```

**Key insight: one event spans many channels, with slightly different times on each.** Event
`id_1` is a single incident that hit channels 12, 13, … 41, 42 … Channel 12 saw it at `20:42`,
channel 41 not until `03:07` the next day — the fault **propagated** through the spacecraft.

Hence the differing counts:
- **3,589 label rows** (one per channel-event pair)
- **200 unique event IDs** (actual incidents)
- For the 41–46 subset: **1,255 rows from 118 unique events**

These are **time intervals**, not points. `id_1` lasted **7 days**.

### 4. `anomaly_types.csv` — what each event means (200 rows)

```
     ID    Class    Subclass    Category Dimensionality Locality       Length
0  id_1  class_6  subclass_1  Rare Event   Multivariate   Global  Subsequence
1  id_2  class_7  subclass_1     Anomaly   Multivariate    Local  Subsequence
```

**`Category`** is the important one:

| Category | Count (M1) | Meaning |
|---|---|---|
| **Anomaly** | 118 | A genuine fault |
| **Rare Event** | 78 | Unusual but *intentional* — e.g. a commanded manoeuvre |
| **Communication Gap** | 4 | Lost contact. Not a spacecraft fault |

> ⚠️ **The benchmark's central difficulty:** anomalies and rare nominal events look
> statistically identical. The ESA-ADB paper states no algorithm can separate them, which is why
> the official metric scores them **combined**
> (`select_labels={"Category": ["Rare Event", "Anomaly"]}`).

Other columns (regenerated by `infer_anomaly_types.py`):

- **Dimensionality** — Multivariate (164) vs Univariate (32)
- **Locality** — Global (113, value is extreme in absolute terms) vs **Local** (83, value looks
  normal but is wrong *for the context*). **This predicts which algorithms work.**
- **Length** — Subsequence (184) vs Point (12)

Mission 2 for comparison: 644 events — **31 anomalies, 613 rare events**, 635 multivariate,
585 global, all subsequence. Rare-event dominated, which is why the paper calls M2-lightweight
"trivial".

### 5. `telecommands/` — commands sent *up* to the satellite

```
telecommands.csv: 698 commands, Priority {0:345, 1:323, 2:19, 3:11}

telecommand_36.zip:  66 firings in 14 years
2007-04-17 17:34:34.383    1
2007-05-10 06:38:56.256    1
```

Sparse events — value is always `1` = "fired at this instant". There are no "off" rows; absence
is the off state.

**Why they matter:** if operators command a mode change, sensors *will* jump — that's expected,
not an anomaly. The ESA-ADB paper flags telecommands as **requirement R6, which no benchmark
algorithm satisfies.** This is an open opportunity (see `docs/05-NEXT-STEPS.md`).

Priority scale is 0 (low mission impact) → 3 (high). The official preprocessing keeps only
**priority ≥ 3**: 11 of 698 for M1, 4 of 123 for M2.

## The benchmark subsets

Full channel sets are a compute trap (the original paper hit OOM on several algorithms). Real
work happens on the **lightweight subsets**:

| Mission | Lightweight channels | Count | Character |
|---|---|---|---|
| **Mission 1** | `channel_41` … `channel_46` | **6** | correlation 0.97–1.00, contextual anomalies. **Hard.** |
| **Mission 2** | `channel_18` … `channel_28` | **11** | median correlation 0.03, global rare events. **Easy.** |

That contrast — one mission where sensors are near-identical, one where they're independent — is
what makes cross-mission federation genuinely non-IID and scientifically interesting.

## Published baselines to beat

Corrected event-wise F0.5, lightweight subsets (Table 4 of the ESA-ADB paper):

| Algorithm | Mission 1 | Mission 2 |
|---|---|---|
| **Telemanom-ESA Pruned** | **0.786** (P=0.999, R=0.424) | 0.842 |
| **Windowed iForest** | <0.001 | **0.949** |
| Telemanom-ESA (non-pruned) | 0.178 | 0.224 |
| DC-VAE-ESA STD5 | 0.075 | 0.079 |

Note the 0.178 → 0.786 jump for Telemanom. **Same neural network** — the entire difference is a
post-processing pruning step. On this benchmark the detection pipeline matters more than the
architecture.

## The evaluation metric

```
corrected event-wise precision:  Pre = TPe/(TPe+FPe) × (1 − FPt/Nt)
corrected event-wise F-beta:     Fβe = (1+β²)·Pre·Rece / (β²·Pre + Rece),  β = 0.5
```

Two things make this brutal:

1. The `(1 − FPt/Nt)` factor penalises the **total duration** of your false positives.
2. β = 0.5 weights **precision 4× more than recall**.

So the winning strategy is *flag almost nothing, but be right when you do*. Telemanom-Pruned
catches only 42 % of events yet scores 0.786 because its precision is 0.999.

Also relevant: high-dimensional false-alarm amplification, `P(FP_system) = 1 − (1 − p_fp)^N` —
which is why full-channel-set scores collapse relative to lightweight subsets.
